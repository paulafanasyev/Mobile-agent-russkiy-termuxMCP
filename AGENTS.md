# AGENTS.md — правила разработки Mobile Agent Русский TermuxMCP

## 1. Назначение проекта

Это русскоязычный мобильный ИИ-агент для Android с локальным и облачным ИИ, MCP/TermuxMCP, голосовым интерфейсом, планировщиком, памятью, документами и сетевым уровнем Firewall/VPN на базе libbox.

Главная цель — дать пользователю единый безопасный интерфейс для выполнения разрешённых задач на телефоне и управления подключёнными агентами и API.

## 2. Язык

- Пользовательский интерфейс, системные сообщения, документация и новые тексты — на русском языке.
- Английский допускается только там, где он технически необходим: имена API, классов, пакетов, команд, URL, переменных окружения и внешних протоколов.
- Не переводить идентификаторы исходных библиотек и публичные API, если это нарушит совместимость.

## 3. Архитектура

Слои проекта должны оставаться разделёнными:

- UI/UX Android/Expo;
- Светлана — пользовательский ИИ-интерфейс и оркестратор;
- Agent Orchestrator — единая маршрутизация задач;
- MCP/TermuxMCP — инструменты и выполнение команд;
- Provider layer — локальные и облачные модели/API;
- Memory/Skills/Scheduler — память, навыки и планировщик;
- Android native modules — устройство и системные возможности;
- Firewall/VPN — сетевой контур;
- libbox — нативный сетевой движок.

Не смешивать эти слои без необходимости.

## 4. Светлана и ИИ-агенты

Светлана должна использовать общий безопасный инструментальный слой, а не получать отдельный неограниченный shell-доступ.

Любое действие агента проходит через разрешения/политику инструмента.

Опасные операции должны требовать явного подтверждения пользователя либо заранее созданной пользователем политики.

Поддерживать несколько провайдеров и возможность переключения между ними. Локальная модель должна иметь возможность работать без сети, когда подходящая модель установлена на устройстве.

## 5. TermuxMCP и команды

- Не выполнять произвольные команды без политики доступа.
- Команды должны логироваться с результатом и статусом.
- Для долгих задач поддерживать отмену и контроль выполнения.
- `/loop` должен иметь ограничение по времени/итерациям и возможность остановки пользователем.
- Не хранить секреты в исходниках или логах.

## 6. Android и устройство

Доступ к функциям Android предоставлять через нативные модули с минимально необходимыми разрешениями.

Не добавлять опасные Android-разрешения только ради удобства.

Перед изменением системных параметров, удалением данных, установкой приложений, отправкой внешних сообщений или другими потенциально необратимыми действиями использовать подтверждение/политику.

## 7. Firewall/VPN/libbox

- Firewall не должен объявляться запущенным, если настоящий libbox не найден и не инициализирован.
- `libbox.aar` не коммитить в Git: он является воспроизводимым артефактом сборки.
- Версия исходника sing-box/libbox должна быть закреплена commit SHA.
- Перед релизом проверять SHA256 AAR.
- Любой bridge между `VpnService` и libbox должен работать с реальным API AAR; не использовать заглушки, выдающие себя за forwarding.
- Изменения сетевого слоя проверять на запуск, остановку, DNS, маршрутизацию и обработку ошибок.

## 8. API-ключи и секреты

- Не коммитить API-ключи, токены, cookies, приватные ключи и пароли.
- Хранить секреты в Android Keystore/защищённом хранилище либо в секретах CI.
- В интерфейсе показывать ключи замаскированными.
- Для каждого провайдера хранить только необходимые данные.

## 9. Документы и файлы

Работа с файлами должна использовать sandbox/разрешения приложения. Перед удалением или массовым изменением файлов требуется подтверждение, если действие не разрешено пользовательской политикой.

## 10. Сборка и проверка

Перед коммитом по возможности выполнять:

```bash
pnpm install --frozen-lockfile
pnpm test
pnpm exec tsc --noEmit
bash scripts/verify-android-agent.sh
```

Android native build должен выполняться в воспроизводимом CI с Android SDK/NDK и фиксированными версиями.

## 11. Изменения и Git

- Не делать `git push --force` в `main`.
- Не удалять lock-файлы для обхода ошибок сборки.
- Не выдавать непроверенное за готовое.
- После существенных изменений выполнять повторную проверку.
- Один логически завершённый этап — один понятный commit.

## 12. Expo

Перед изменением Expo-конфигурации сверяться с версией Expo, указанной в `package.json`, и использовать соответствующую официальную документацию.

Не полагаться на устаревшие примеры из других версий Expo.

## 13. Критическое правило

Если функция ещё не подключена к реальному runtime, не называть её готовой. Явно различать:

- реализовано и проверено;
- реализовано, но требует runtime-проверки;
- каркас/заготовка;
- отсутствует.
